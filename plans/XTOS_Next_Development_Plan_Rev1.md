# XTOS后续开发计划 Rev.1

**更新时间**: 2026-09-30
**适用范围**: Linux 6.6 + PREEMPT_RT、x86_64/ARM64/RISC-V、BCI、AR/VR、AI运行时
**当前阶段**: M1基础环境已完成；调度器和BCI代码处于集成审计阶段

## 一、当前真实状态

已确认：

- Linux 6.6.0-rt15内核源码和x86_64 bzImage存在。
- ARM64、RISC-V交叉编译工具链和QEMU已配置。
- XTOS调度器源码和BCI源码已生成。
- `xtos_sched.o`曾单独编译成功。

尚未确认：

- XTOS调度器是否已经安全接入Linux主调度路径。
- BCI框架是否已经接入内核Kconfig/Makefile并可编译为模块。
- 完整内核是否包含XTOS代码并可启动。
- 真实EEG设备、FPGA、AR/VR设备上的端到端性能。

因此，当前不能把XTOS称为已经完成的实时操作系统；下一阶段的第一目标是完成集成门禁和可重复验证。

## 二、开发原则调整

### 1. 不直接替换Linux主调度器

第一版本不修改Linux默认调度类，也不把一个独立的优先级队列文件伪装成主调度器。XTOS先采用以下层次：

- Linux 6.6 + PREEMPT_RT作为实时内核基础。
- `SCHED_FIFO`/`SCHED_RR`/`SCHED_DEADLINE`作为第一阶段可验证的实时调度机制。
- `libxtos-rt`提供CPU隔离、线程优先级、内存锁定、定时器和性能追踪封装。
- XTOS调度策略作为可选内核组件或用户态控制平面逐步验证。
- 只有在基准测试证明现有机制不足后，才考虑深入实现自定义`sched_class`或升级内核版本使用`sched_ext`。

### 2. 不把GPU抢占作为早期硬实时承诺

GPU上下文抢占能力由硬件、驱动和运行时决定，不能仅靠用户态代码保证1ms抢占。早期采用：

- 硬实时路径不依赖GPU。
- EEG预处理和安全响应保留CPU路径。
- AI推理作为软实时任务，设置截止时间和超时降级策略。
- 等有明确GPU型号后，再分别适配CUDA、ROCm或其他NPU运行时。

### 3. FPGA不是当前阻塞项

没有FPGA板时，先完成CPU软件路径、数据回放、QEMU和性能基准。FPGA仅在profiling证明CPU无法满足目标后进入硬件加速阶段。

### 4. BCI硬件驱动优先采用用户态适配

对串口、BLE和网络型EEG设备，第一版优先使用Linux已有串口/USB/Bluetooth/网络栈，在用户态完成协议适配；内核驱动只保留真正需要低延迟、DMA或硬件中断的部分。这样可以降低内核崩溃风险，并支持更多通用设备。

## 三、当前阶段：集成审计与构建门禁

### 任务A：调度器审计

- 增加`CONFIG_XTOS_SCHED`，默认关闭。
- 检查每CPU运行队列、任务生命周期、锁和哈希表释放路径。
- 删除或隔离未真正接入Linux调度路径的误导性接口。
- 先提供用户态可测试的O(1)优先级队列实现。
- 执行完整内核配置、编译和错误修复。
- 记录“对象编译”“完整内核编译”“真正调度集成”三个独立结果。

### 任务B：BCI框架审计

- 增加`CONFIG_XTOS_BCI`和设备子选项，默认关闭。
- 接入`drivers/Kconfig`和`drivers/Makefile`。
- 检查DMA缓冲区释放、mmap生命周期、读写锁和并发访问。
- 检查OpenBCI协议实现是否符合Linux串口驱动模型；不符合时改为用户态串口适配器或明确保留为实验骨架。
- 编译内核模块和用户空间库。
- 无硬件时运行错误路径、模拟数据和回放测试。
- 记录“模块编译”“用户库编译”“真实EEG验证”三个独立结果。

### 阶段验收标准

- `make olddefconfig`成功。
- `make bzImage`成功，或记录可复现的真实失败原因。
- `make M=drivers/xtos modules`成功，或记录阻塞点。
- 调度器用户态单元测试通过。
- BCI用户库能在无设备时正确返回错误，不崩溃、不泄漏。
- QEMU至少能启动基础内核或完成内核镜像检查。

## 四、后续12个月路线

### Phase 1：内核与驱动集成，当前优先级最高

**目标**：得到可重复构建的XTOS开发版。

内容：

- 修复Kconfig、Makefile和内核API问题。
- 完成x86_64内核集成。
- 完成ARM64和RISC-V交叉编译。
- 建立QEMU启动和串口日志测试。
- 建立CI：构建、静态检查、用户态测试、模块编译。
- 完成集成审计报告。

交付物：

- `xtos-kernel-x86_64`
- `xtos-kernel-arm64`
- `xtos-kernel-riscv64`
- 可重复构建脚本
- 集成测试报告

### Phase 2：实时运行时与性能基线

**目标**：先用Linux已有实时能力实现可用的XTOS运行时。

内容：

- `libxtos-rt`：优先级、CPU affinity、`mlockall`、高精度时钟、deadline、错误处理。
- 实时线程模板和进程启动器。
- CPU隔离、IRQ affinity、频率策略和内存锁定配置工具。
- cyclictest、timerlat、osnoise和自定义数据流延迟测试。
- 统一指标：p50、p95、p99、p99.9、最大值，而不是只报告平均值。

交付门槛：

- 在实际目标硬件上取得可重复的延迟数据。
- 把“非RT宿主机基线”和“XTOS RT内核结果”分开报告。
- 不在QEMU结果上宣称真实硬件实时性能。

### Phase 3：BCI数据平面与设备兼容层

**目标**：在没有真实EEG硬件时先完成可测试的数据通路。

内容：

- EEG样本统一格式：通道、采样率、单位、时间戳、质量标记。
- 文件回放设备和虚拟EEG设备。
- 串口、BLE、USB和网络设备的用户态适配接口。
- LSL或等价时间戳接口。
- 环形缓冲区、背压、丢包统计和数据质量监控。
- 首批优先支持OpenBCI兼容串口数据；其他厂商使用插件接口，不虚构协议兼容。

交付门槛：

- 回放数据经过完整采集、滤波、推理和输出链路。
- 可测量端到端延迟和丢包率。
- 无设备条件下测试可自动运行。

### Phase 4：确定性信号处理管线

**目标**：建立可复现的EEG实时处理基础。

内容：

- 采样率转换和时间戳校正。
- 0.5-100Hz带通、陷波、伪迹标记。
- FFT、功率谱和基础时域特征。
- P300和SSVEP优先实现。
- Motor Imagery作为研究路径，不预先承诺准确率。
- C实现和Python参考实现逐项对比。
- 处理超时、数据缺失和质量不足时的安全降级。

交付门槛：

- 每个处理模块有参考输入和黄金输出。
- 误差、延迟、CPU占用和内存占用有自动测试。
- 不把模型准确率当作系统实时性的替代指标。

### Phase 5：AI运行时

**目标**：让AI推理成为可管理的软实时任务，而不是硬实时承诺。

实施顺序：

1. ONNX Runtime作为统一部署后端。
2. PyTorch模型导出和验证。
3. TensorFlow/TFLite模型导出和验证。
4. CPU推理基线：x86 AVX2、ARM NEON、RISC-V标量路径。
5. INT8/FP16量化基准。
6. 推理超时、模型不可用和低置信度降级。
7. 有实际GPU后再实现CUDA/ROCm后端。

交付门槛：

- 同一模型在PyTorch、ONNX和目标运行时的输出误差有报告。
- 每种硬件分别记录延迟分布。
- 没有GPU时不宣称GPU抢占能力。

### Phase 6：多架构验证

**目标**：支持通用x86_64、ARM64和RISC-V，而不是泛泛声称支持所有设备。

内容：

- x86_64服务器真实构建和运行。
- ARM64通用QEMU和至少一种真实开发板验证。
- RISC-V QEMU启动和用户态库验证。
- 架构相关代码隔离在明确目录和接口中。
- 不为Apple Silicon编写未经验证的设备树；Apple设备支持应另行评估。
- 每个平台有独立的性能和功能矩阵。

### Phase 7：AR/VR与多模态

**前置条件**：至少具备一套可访问的AR/VR设备和眼动/EMG数据源。

内容：

- OpenXR应用层适配，不把OpenXR头显驱动放进XTOS内核。
- EEG事件映射为XR action。
- EEG、眼动、EMG统一时间戳和质量标记。
- 置信度融合、确认机制和撤销机制。
- 实时渲染线程与BCI推理线程隔离。
- 交互延迟、误触发率和疲劳状态分别测试。

交付门槛：

- 先用模拟XR事件完成自动化测试。
- 真实头显测试必须单独记录设备、固件、运行时和延迟。
- 不把意念控制用于真实轮椅、机械臂或其他危险设备，除非完成独立安全认证和冗余急停设计。

### Phase 8：安全、发布与生态

内容：

- reproducible build和版本锁定。
- SBOM、依赖漏洞扫描、静态分析和模糊测试。
- GPL、Apache、第三方模型和数据集许可证审查。
- 完整API文档、故障排查和设备适配指南。
- 社区版发布，明确标注实验性模块。
- 医疗用途与消费级用途分开，不把社区版宣称为医疗器械软件。
- 发布前完成真实硬件矩阵和回归测试。

## 五、近期执行顺序

按以下顺序推进，不跨越构建门禁：

1. 完成调度器和BCI集成审计。
2. 修复并验证Kconfig、Makefile和内核API。
3. 编译完整x86_64内核和BCI模块。
4. 构建用户态BCI库和无硬件测试。
5. 用QEMU启动内核或完成镜像级验证。
6. 建立虚拟EEG回放通路。
7. 实现`libxtos-rt`和实时性能测试套件。
8. 接入ONNX Runtime，建立CPU推理基线。
9. 再推进P300/SSVEP和AR/VR适配。
10. 最后进行真实硬件、跨架构和发布验证。

## 六、当前外部资源缺口

现在可以继续开发，不需要立即补充信息；但以下资源决定后续验证边界：

- 一台真实ARM64开发板：用于替代QEMU做实时性验证。
- 一台真实RISC-V开发板：用于硬件级启动验证。
- 一套通用EEG设备：建议先选OpenBCI兼容串口设备。
- 一套AR/VR设备：用于OpenXR真实交互测试。
- FPGA开发板：仅在CPU profiling证明必要后采购。
- 若做医疗产品，还需要独立的法规、质量体系和临床/安全验证资源。

## 七、阶段性发布定义

### XTOS Developer Preview

必须具备：

- 可重复构建的RT内核。
- 可选XTOS模块。
- 用户态实时运行时。
- 虚拟EEG回放。
- 基础BCI处理和ONNX推理。
- x86_64可运行，ARM64/RISC-V可交叉编译或QEMU验证。

### XTOS Hardware Preview

额外必须具备：

- 至少一套真实EEG设备采集。
- 至少一种ARM64或RISC-V硬件验证。
- AR/VR设备真实链路。
- 端到端延迟、丢包和稳定性报告。

### XTOS 1.0

额外必须具备：

- 发布矩阵中的所有目标平台通过回归测试。
- 明确的ABI/API稳定性承诺。
- 安全审计、许可证审计和SBOM。
- 文档、示例、安装包和升级/回滚机制。
- 所有性能数字有可复现实验条件。

**计划状态**: 当前执行Phase 1集成审计；后续阶段按构建和验证结果推进。
